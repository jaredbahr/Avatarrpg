## Amendment (owner, 2026-11-15): newest green commit, not exact HEAD

The exact-HEAD rule above ("no older-green fallback") is replaced. On a busy day every merge cancelled the previous main CI run, so main rarely finished a full run and Pages had not deployed since 2026-11-08. The owner's decision: the site rebuilds from the **newest commit on main's first-parent history whose CI fully passed**, even while newer commits are still testing, and never from a commit whose CI failed, was cancelled or has not finished.

- `select` walks main's first-parent chain from the live head, at most 50 commits (`MAX_WALK`), and takes the first commit whose newest eligible `ci.yml` run (same workflow identity, `main`, push/schedule/workflow_dispatch events) is completed and successful with every required job and step. A newest run that is failed, cancelled, running, or missing, or whose required jobs are not green, is stepped past; API errors and malformed data still block. If nothing in the walk is green, nothing deploys.
- Every later stage (`before-build`, `before-upload`, `before-publish`) revalidates exactly the selected SHA and run, and now also that the SHA is still an ancestor of main (`compare/<sha>...main` must be `ahead` or `identical`). Main advancing past the selected SHA no longer blocks a deploy.
- The Pages artifact belongs to the deploy workflow run, so its metadata is checked against that run's own SHA; the artifact name still encodes the selected SHA and CI run.
- `fresh` is judged on the selected commit's date (`committed_at`, 25 hours) instead of HEAD's, so a day whose newest green commit is new still deploys.
- `ci.yml`: pushes to `main` no longer cancel each other (concurrency key includes the SHA; pull requests and other events keep cancel-in-progress). Trade-off: a burst of merges runs a full CI for each, instead of only the last.
